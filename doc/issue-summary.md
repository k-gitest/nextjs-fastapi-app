# Issue管理の全体像

このドキュメントは、このプロジェクトにおける
新機能・拡張・既存残課題の管理フローを俯瞰するためのものです。

具体的なIssueの分類・ラベル・記述ルールは `ISSUE.md` を参照してください。

## 新機能・拡張の流れ

1. 新機能・拡張のアイデアが出る
2. GitHub Issueを作成する
   - 未確定の検討段階から作成してよい
3. 要件・設計を検討する
4. 要件・設計が確定したら、規模に応じて分岐する
   - 小規模: 同一Issueを実装用に更新する
   - 大規模: 実装Issueを新規作成し、検討IssueはCloseする
5. 実装する
6. 実装結果を整理する
   - 恒久的な設計判断がある → README/ADRへ反映する
   - 恒久的な設計判断がない → README/ADRへの反映は不要
   - 対応を見送った残課題がある → ISSUE.mdへ追加する
7. GitHub IssueをCloseする
   - 完了記録の書き方は「GitHub Issue Close時の記録」を参照

## 既存の残課題を解消する流れ

1. ISSUE.mdの残課題について対応を開始する
2. GitHub Issueとして管理する
3. 実装・設計判断を行う
4. 恒久的な設計判断があればREADME/ADRへ反映する
5. 対応を完了したらGitHub IssueをCloseする
   - 完了記録の書き方は「GitHub Issue Close時の記録」を参照
6. ISSUE.mdから該当項目を削除する

## それぞれの役割

| 場所 | 役割 |
|---|---|
| GitHub Issue | 新機能・拡張の要件・設計・実装を追跡する場所 |
| README.md | 恒久的な設計・アーキテクチャ判断を残す場所 |
| ISSUE.md | 実装・設計の結果生まれた、今は対応しない残課題を記録する場所（詳細ルールはISSUE.md自体を参照） |

## GitHub Issue Close時の記録

GitHub IssueをCloseする際は、Issue本文に完了記録を残す。

完了記録は「何をしたか」だけでなく、「なぜその対応になったか」「何を確認して完了としたか」が
後から追えることを目的とする。

### 基本構成

```markdown
## 対応結果

何を対応し、最終的にどうなったかを簡潔に記載する。

## 調査方法

調査・切り分けを行った場合、その方法と結果を記載する。
単純な修正など不要な場合は省略可。

## 判明したこと

当初の想定との差異、調査によって判明した原因・対象範囲・設計上の知見などを記載する。
特に、Issue起票時の仮説と実際の結果が異なった場合は残す。

## 対応した内容

変更したファイル、実装内容、ロジックへの影響などを記載する。

## 検証結果

動作確認、テスト、UI確認、ログ確認など、完了と判断した根拠を記載する。
```

### 記載方針

- 完了記録は、将来そのGitHub Issueだけを見ても経緯を把握できる粒度にする
- Issue起票時の想定と実際の結果が異なった場合、その差異を記録する
- 実装内容だけでなく、重要な設計判断や「なぜ変更しなかったか」も必要に応じて記録する
- 不要な項目は無理に埋めない（Issueの性質に応じて基本構成の項目は省略してよい）
- 完了したIssueはISSUE.mdから削除する。完了記録はGitHub Issue側にのみ残し、
  ISSUE.mdへは転記しない（ISSUE.mdは未解決の残課題のみを扱う場所であるため）
